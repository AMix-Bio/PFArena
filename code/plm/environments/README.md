# Conda environments

Each protein model has an independent Conda specification. ESM-2 and
ProGen2-base used the same software stack in the reported experiments, but are
kept as separate files so that either model can be installed and updated
without changing the other environment.

| Model | Environment file | CUDA runtime |
|---|---|---:|
| ESM-2 | `esm2.yml` | 12.8 |
| ProGen2-base | `progen2_base.yml` | 12.8 |
| ProSST-2048 | `prosst_2048.yml` | 12.8 |
| S3F | `s3f.yml` | 12.1 |
| S3F-MSA | `s3f_msa.yml` | 12.4 |
| VenusREM | `venusrem.yml` | 12.1 |

Create an environment from the repository root, for example:

```bash
conda env create -f environments/esm2.yml
conda activate pfarena-esm2
```

The remaining environments are created in the same way:

```bash
conda env create -f environments/progen2_base.yml
conda env create -f environments/prosst_2048.yml
conda env create -f environments/s3f.yml
conda env create -f environments/s3f_msa.yml
conda env create -f environments/venusrem.yml
```

The specifications pin the packages that affect loading, preprocessing, or
model outputs. Transitive system libraries are resolved for the target Linux
platform. `runtime_versions.csv` records the versions observed in the reported
runs and is the reference for runtime verification.

S3F uses CUDA extensions distributed through the `pyg` channel. VenusREM uses
the structure-token cache generated by the ProSST stage and therefore does not
duplicate ProSST's geometry stack. The NVIDIA driver on the target host must
support the CUDA runtime declared by the environment. Model repositories and
licensed checkpoints are obtained from their official sources and are not
embedded in these environment files.

Binary `conda-pack` archives are intentionally not committed: they are large,
platform-specific, and may retain installation paths. If an offline worker
requires one, create it locally only after validating the YAML environment:

```bash
conda install -n base conda-pack
conda pack -n pfarena-esm2 -o pfarena-esm2-linux-64.tar.gz
```
